# Cooperative Warp Execution in Tensor Core for RISC-V GPGPU

**Paper:** Abubakr Nada, Giuseppe Maria Sarda, Erwan Lenormand, et al. · *HPCA 2025* · [Link](https://imec-publications.be/handle/20.500.12860/46074)  
**Critique by:** Miki Korol · 11/12/26  
*Written for CS 254A: Advanced GPU Microarchitecture, UCLA*

---

This paper addresses several challenges pertaining to integration of Tenser Cores (TC) into GPU architectures. They mention that the motivation is because previous research on tensor core optimisations has focused on the volta tensor core architecture and integration with its NVIDIA GPU. These optimisations are good, however the volta gpu is not the latest iteration of NVIDIA GPU’s/Tensor Cores. They also are constrained by the PTX/SASS instructions limiting the dimensions of GEMM the Tenser cores can compute which they claim limits the architectural research capabilities of starting from the volta tensor core. That is why they move to a RISC-V based GPGPU architecture implementation on VORTEX GPGPU allowing them to create custom TC with flexible instructions allowing for a customisable TC applicable to more variations of GEMM workloads. They implement this TC and then discuss other challenges integrating this TC with the GPU, specifically low tensor core utilization when the GPU pipeline hinders the usage of the TC and also challenges with the memory bandwidth and capacity limiting the activity of the TCU.

For the first challenge of scalability and flexibility of the tensor core to different dimensions, they propose altering the K dimension depending on the number of 32FP Dot Product units the tensor core is configured with and also the number of operands that fit into the 32bit memory words. This allows the tensor core to adapt to GEMM on different data sizes. This tile is also split into Ot steps in which the A and B operands are reused while the C data changes. Because of this they only load A and B into a dedicated cache for A and B operands, reducing the requirements for warps to stay active. Another problem is that the scaling of some parameters such as the outer dimension improves the utilization and reuse of data but increases the accumulator size which must be held in the register file due to constant updating resulting in a memory bottleneck. They apply different hardware and software optimisations  they call cooperative warp execution in which they execute warp groups in tandem allowing for larger outer product sizes. To do this they implement a tile buffer where warps work together to do the OT steps accumulating the results for a given output tile thus decoupling the TC from stalls and memory bottlenecks. Similarly they implement cooperative flushing of the tile buffer using several warps to bring back the completed tile to memory and their independence also allows for the tile buffer to continually be used either for accumulation or flushing. This warp cooperation is also linked to tensor core utilisation increase because if warps work on the same tile then they will not be dependent on each other and freely run reducing divergence and stall time.

Results note a disappointing utilization for most thread and DPlen permutations when there is no cooperative warp execution. But, when they activated cooperative warp execution, the utilisation was better consistently achieving at least 50% and with larger K values they showed an approach towards 100% average utilization as well as close to 60% memory bank utilization showing that the memory and execution times are well balanced. I will mention later that although this is true I don't think they explained why this is the case well and how their optimisations guarantee to achieve this although it is a good result and wherever it came from it shows good GPU/TPU pipeline decoupling and throughput capabilities.

This paper's strength is that it focuses on the challenges of implementing a more flexible TC into GPU pipelines rather than optimising a very specific outdated TC and GPU pipeline thus pushing the boundaries for future TC research and allowing others to come implement their own optimisations to the flexible design. The flexibility comes with the focus on implementing their design on VORTEX GPGPU with its custom instruction capabilities. They do a good job of pointing out the challenges (flexible tile size), memory bottlenecks, and GPU/TPU pipeline coupling challenges. They also give solutions to all of these although the explanations are a little hard to follow at times and sometimes they make claims that I do not understand how they got to.

One sentence stood out to me as possibly an assumption or maybe they just need to explain it better it is “We tie the size of the K dimension to hardware resources determined by DPlen to ensure full utilization of the dot product lanes for each load operation; such choice guarantees balance between load and compute phases, as shown in Figure 3-a. ” (Page 1425 Second To Last Paragraph) How they determine that this choice guarantees balance between the load and compute phase is not explained from my perspective you are performing a load optimisation by operating on reusable data so it should hinder the execution a little by increasing the steps but improve the reusability of the data but the ratio of computation to load time is not explained and how this evens it out is hard to understand.

Overall the paper does a good job of explaining the flexible architectures possible on RISC-V based GPUs like VORTEX and the challenges that come with pairing a TC with a GPU pipeline. This is relevant to industry and research as it pushes the boundary of performance and outlines challenges one will face if they want to implement a similar TC and optimize it.
