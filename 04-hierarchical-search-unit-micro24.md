# Extending GPU Ray-Tracing Units for Hierarchical Search Acceleration

**Paper:** Aaron Barnes, Fangjia Shen, Timothy G. Rogers · *MICRO 2024* · [Link](https://par.nsf.gov/servlets/purl/10591702)  
**Critique by:** Miki Korol · 11/19/26  
*Written for CS 254A: Advanced GPU Microarchitecture, UCLA*

---

This paper addresses two main challenges. The first challenge is that the use of the ray tracing unit is locked behind Application Programming Interfaces (APIs) that only understand BVH tree traversals with axis aligned bounding boxes and triangle primitives. This means programmers who want to use the ray tracing unit for other tree traversal applications have to convert their tree traversals to fit into the Graphics API mold. The second challenge is limited generalizability of the RTU which leaves it as unused hardware on non ray tracing workloads. The primitive tests ray box and ray triangle intersection tests are not general enough to apply to more applications.

The authors introduce several changes to solve these two issues. As for the first challenge of the API wall to the ray tracing unit they expose RTU tests to CUDA C++ users which they can call to use the RTU pipeline from the GPUs general compute interface rather than from APIs. This allows the users to access the RTU functionality without the need for the API and create their own custom tree traversal algorithms only sending the node tests to the RTU when they need the pipeline calculations functionality. This way users define their tree/graph in software, create the traversal loop and call the RTU to compute the node results. The tree or graph no longer needs to fit the API mold allowing for a more generalisable RTU application space.

The second issue is the limited primitives supported by the RTU. The RTU natively only supports two computations in the pipeline (axis aligned bounding box ray intersection and triangle ray intersection tests) making it perfect for mesh based graphics rendering workloads. The paper notes that with minimal pipeline changes they can incorporate three more functionalities of the pipeline extending the generalizability and applicability of the RTU. The first new supported operation in the pipeline is squared euclidean distance calculation between two 16 dimensional arrays. Each dimension is a 32 bit float and the squared distance is calculated as the sum\[(yi-xi)^2\]. The second operation is the angular distance of two 8 dimensional arrays again stored as 8 fields of 32 bit floats and computed with a dot sum over the norm sum and returned as two values to not include the slow and complicated division in the RTU pipeline. The final added operation is a key compare operation which compares a key value with up to 36 compare values and returns a bit per value that holds the comparative value of the key to the value. If the value \> key then bit \== 0 and 1 otherwise. The reason it is called the RTU pipeline is because they use pipeline registers to split the computation into chunks. Not all chunks are used for all computations. There is a control signal unit that controls which operations will be active depending on the instruction type.

As stated before the RTU pipeline functionality is exposed to the users. They mention that from the GPU general compute interface AKA CUDA C++ for example the users can call these functionalities. For example they can use \_\_euclid dist(a, b, N), and \_\_angular dist(a, b, N) functions to get the distance and angle between two N dimensional arrays from the kernel. These can be used independently or in a loop to traverse a tree or graph and find important values like the nearest neighbor

After developing and synthesizing the unit modeled inside of a volta GPU they mention that the power and area are not yet accurate. They tested on a large number of different sizes and shapes of trees and graphs. B-Trees, point clouds, KD-Trees and more. The most impressive results are 33.9% speedup on BVH nearest neighbor traversal and large memory savings and speedups on a lot of other traversals.

As discussed the main takeaways are that one they used a software based tree traversal algorithm only implementing the RTU pipeline tests in hardware which likely reduces hardware area, two they removed the need for using APIs to access the RTU functionality, and three they extended the RTU pipeline to include more operations allowing it to apply to a more general tree and graph search.

I think the technical aspects are original, especially the extension of the RTU usability within the kernels making it easily accessible and usable by a more general population as well as the functionality extension. They do a good job of explaining most of the tradeoffs of such an architecture.

They seem to leave out some stuff, maybe by accident but I suspect one on purpose. The first is not too bad; they seem to have left out what the users are meant to call the key-compare functionality of the RTU. They gave two functions that do the distance and angle computation but don't list the other functionalities. I'm sure they exist but they did not explain them as clearly as the shown functions mentioned before. The other thing they fail to comment on is the GPU utilization. The traversal including data storage and traversal stack and other values are handled in software that means there will be registers allocated for them within the kernel warps. If there are too many registers per warp or kernel then the GPU utilization might suffer from unbalanced resource usage like we learned at the start of the class. This is not mentioned in the paper, only the hardware accelerator usage is mentioned.

Another issue with this implementation is relevance. Unfortunately for this paper the number one GPU manufacturer is NVIDIA with more than 90% of the market share and NVIDIA chooses to implement their RTUs using a hardware based tree traversal stack and internal memory offloading the entire job to the hardware. This makes their implementation not relevant to NVIDIA GPU architectures thus losing a big portion of the market interest in this sort of modification.
